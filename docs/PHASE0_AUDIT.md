# Phase 0: seed audit and the decisions it forces

Generated by `npm run audit` (raw output: `PHASE0_AUDIT.txt`). Re-run it after any
change to `seed.json`.

Spec section 6 lists six things to fix before Phase 1. The audit confirms all six and
finds **six further problems that will fail an insert or load ambiguously**, which
section 6 does not mention. Those are the blockers below.

## What the seed actually contains

| | |
|---|---|

| stage groups | 7 (CLAUDE.md says 8) |
| substages | 21, of which 20 are distinct within their stage group |
| deliverables | 58 |

| assignment rows | 70 |

## Blockers

Each one either violates a check constraint in the spec's own schema or cannot be
resolved to a row. None can be deferred past Phase 1.

### B1. Three of the five role markers are not valid role codes

The sheet uses `DD`, `WD`, `ID`, `.` and `-`. The schema allows
`PI, DD, WD, PE, CL, INVOLVED`. So 28 of 70 assignment rows fail on insert.

| marker | rows | reading |
|---|---|---|
| `.` | 21 | oversight; 16 of them Gururaj Sir, the principal |
| `-` | 5 | a person is named, no role recorded |
| `ID` | 2 | a discipline written into the role column (Selva, Vibhaas) |

**Resolved, with evidence.** Mapping `.` and `-` to `INVOLVED` and `ID` to `DD` is the
only reading that reproduces *both* numbers the spec asserts about itself: Madhu = 14
(Phase 1 acceptance) and Selva = 7 (Team-load screen). `npm run seed:dry` asserts both
and exits non-zero if either drifts.

### B2. `MATERIAL SELECTION` appears twice inside one stage group

Spec 6.6 says it appears three times "under different stage groups" and prescribes
showing the stage group next to the name. That is not the whole problem: two of the
three are both in `GFC-ID`, at seq 17 and seq 20. Showing the group name disambiguates
nothing, and four projects reference it twice.

Project rows name substages by `(group, name)`, so neither the seed nor a user can tell
the two apart. **Needs a decision** — see Open questions.

### B3. `planned_weeks` is the string `"NA"`

On `STRUCTURAL DRAWINGS TILL PLINTH`. The column is `numeric`. Loads as null.

### B4. Four rows have status `unknown`

Not in the allowed set. These are cells the spreadsheet gave a date but no colour.
A date on a not-done row reads as a target, not a conclusion — `Anup Embassy Springs`
carries one on an explicitly in-process row. **Needs a decision.**

There is a second-order problem here. `stamp_and_log()` nulls `concluded_on` on any
status change away from `done`. Seeding a date onto a non-done row stores a value that
the first dropdown change erases with no warning. Five rows are in this state. The seed
drops those dates rather than storing something that silently vanishes.

### B5. One row carries a note the schema cannot hold

`Ajay Kabra, Veerasandra / SECONDARY ELEVATION` is `in_process` with note `"HOLD"`.
`project_substage` has no note column. Resolved: the schema has a `hold` status, so the
row loads as `hold`. This is the only note in the file, so no note column is warranted.

### B6. Seven projects have `status: null`

`projects.status` is `NOT NULL`. All seven also have null priority and no substage rows —
a distinct tranche in the sheet. The column default `ongoing` would put seven enquiries
on the live board. Seeded as `not_confirmed`. **Confirm this reading.**

### B7. `project_deliverable` is left without RLS

Not a seed problem but found in the same pass. The spec's `enable row level security`
list omits `project_deliverable`, while its policy prose grants insert and update on it.
As written it would be the one table readable and writable by anyone holding the public
anon key. `0003_rls.sql` enables it and flags the deviation in a comment.

## Decisions for the firm

These load without error. The problem is that the value is wrong or carries no
information.

**D1. The board's headline number is blank on day one.** No row has `started_on`;
nothing in the spreadsheet recorded it. `days_in_substage` and `days_over` both derive
from it, so all 37 rows tie at null and the table's sort key is empty. Phase 5's
acceptance test — "the board sorts by longest overrun and the top row is a project you
already knew was stuck" — cannot pass from seeded data, only from statuses moved inside
the app afterwards.

The seed does **not** back-fill start dates. An invented date would feed every overrun
figure the tool exists to produce, permanently and undetectably. CLAUDE.md rule 2.

**D2. 13 of 21 substages have no `planned_weeks`,** including all of `GFC - ARCHITECTURE`
and all of `GFC-ID`. `days_over` is null whenever `planned_weeks` is null, so even once
start dates accumulate, a project sitting in any GFC substage can never appear as
overrunning. That is most of the late-stage work.

**D3. 20 of 37 projects have no substage data** (spec 6.1). CLAUDE.md says show them as
"Not set" and never hide them; spec 6.1 says decide per project whether to track it.
Both can hold, but someone has to mark which are live and which are dormant.

**D4. Priority is 3 on 25 of 37 projects, 68%** (spec 6.2). Values present: 0, 1, 2, 3
and null. A field where two thirds of rows share a value cannot order anything.

**D5. No project has a code, client name or site location** (spec 6.3, 6.4). Spec 6.3
says 13 codes exist in the spreadsheet — they did not survive the decode. Either
re-extract them from the xlsx or the columns ship empty.

**D6. `Mukesh Gala` (sl 25) and `Muskesh Gala` (sl 34)** are one edit apart and both ID
(spec 6.5). Both load. Merging is destructive and is a client-identity question, so it
stays a decision made in the app, not by this script.

**D7. Seven stage groups, not eight.** CLAUDE.md says eight. Either one was lost in the
decode or the doc is stale. It matters: `v_board` picks the current substage by
`(stage_group.seq, substage.seq)`, and `stage_groups.seq` is not in `seed.json` at all —
it is derived from array order, so that order is load-bearing.

**D8. Vanisree has no assignments** and appears only in `people`. She loads as an active
member with zero load.

## Minor, no decision needed

- `sl 32` is used twice (`Navin and Swati Chapperia`, `Hotel Project, Hyderabad`) and

- Typos carried into the taxonomy: `SPACE OPTIMZATION IN CIVIL`, `Basic Structual

## Decisions taken in the Phase 0 review

All five open questions are closed. Each is encoded in exactly one place, the
`DECISIONS` block at the top of `scripts/seed.mjs`, and nowhere else.

| | Question | Decision |
|---|---|---|
| B2 | One `MATERIAL SELECTION` repeated, or two rounds? | **Two rounds.** Both load, renamed so project rows can reference them |
| B4 | Bare dates: finished, or a target? | **A target.** New `target_date` column, migration 0004 |
| B6 | Seven null-status projects: enquiries or live? | **Live**, never filled in. They take the `ongoing` default |
| D4 | Priority: drop or redefine? | **Keep and re-rank in the app.** Loaded as-is, nulls included |
| D5 | Codes and site location | Not decoded, columns ship empty. Re-extract from the xlsx later |

### B2 in detail

The two rounds are seeded as `MATERIAL SELECTION - ROUND 1` (seq 17) and
`MATERIAL SELECTION - ROUND 2` (seq 20). Those names are **positional placeholders, not
studio vocabulary** — they should be renamed in Settings to whatever the studio actually
calls the two rounds. Renaming a substage is safe at any time and needs no warning
(spec section 4, rule 3); nothing downstream depends on the text.

Five projects reference the name. Four reference it twice and take the two rounds in
sheet order; `Vinay Kothari` references it once and takes round 1. In all four
double-referencing projects both mentions carry the same status, so the ordering cannot
produce a wrong result. `Kuldeep Garg`'s `MATERIAL SELECTION` is in `GFC - ARCHITECTURE`,
is unique within that group, and is not renamed.

### B4 in detail

Migration `0004_target_date.sql` adds `project_substage.target_date` and rebuilds
`v_board` to expose it as `days_past_target`. Five rows carry a date.

`target_date` is deliberately outside the trigger's control. It is the one date a user
may author, because it is a plan rather than a record of what happened; `started_on` and
`concluded_on` remain stamped and unauthorable per CLAUDE.md rule 2.

This partly answers D1. No row has `started_on`, so `days_over` is null for all 37
projects and the board's primary sort key is empty on day one. `days_past_target` gives
the board a second, independent signal that has real data behind it from the start —
five projects, four of them already past their target as of this writing.

## Still true after the review

D1 (no start dates), D2 (13 substages with no planned weeks), D3 (20 projects with no
stage data), D6 (Mukesh / Muskesh Gala), D7 (seven stage groups, not eight) and D8
(Vanisree unassigned) are unchanged. None blocks Phase 1. D1 and D2 together mean the
board's overrun column stays thin until the app has been in use for a few weeks, which
is inherent to replacing a system that never recorded start dates.
